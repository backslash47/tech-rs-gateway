# Silent transmitter test: i-3 PLUS OT and i-1M

This standalone ESPHome profile tests whether a powered MAX3232 transmitter alone disrupts communication with the additional valve. It holds the ESP pin feeding the transmitter at logic HIGH (UART idle). The converter output stays connected and driven. The application sends no bytes, including startup, acknowledgments or polling. GPIO levels during chip reset and ROM boot are outside application control.

1. Save your working gateway YAML and firmware for USB restoration. Use a classic **ESP32-WROOM-32**, with the MAX3232 powered as in the working installation. The profile assumes the converter supply is continuously powered, not GPIO-switched.
2. Check **which ESP GPIO actually feeds the MAX3232 TTL transmitter input** in your working installation. GPIO17 in `config/diagnostic-silent-tx.yaml` is an example, not a wiring recommendation. Change `tech_tx_pin` to match; do not move that wire. Do not use this test with a boot console/USB serial pin (especially GPIO1/U0TXD on classic ESP32), a flash pin or a strapping pin. If unsure, report your pin assignment first.
3. With the controller powered down, disconnect the gateway RJ12. Compile and flash the diagnostic over USB with ESPHome (`esphome run config/diagnostic-silent-tx.yaml --device <USB-port> --no-logs`). No web interface or OTA is expected. Keep the same USB supply arrangement as before. If a scope is available, verify the converter TTL input remains HIGH and the RS output remains at its idle level after boot.
4. Verify normal i-1M updates on the i-3 with the gateway disconnected. With power off for cable changes, reconnect the normal three wires including TX, and repeat with the diagnostic already booted and powered. Watch **the i-3 display**, not the gateway: record whether temperatures continue updating or a communication alarm appears after startup settles. No pump or target changes are needed. If communication is lost, disconnect the diagnostic and verify recovery.
5. If it still fails with silent TX, the powered output/wiring is implicated independently of ST-505 frames. If it works silently but fails with the normal firmware under the same conditions, investigate active transmission (frame timing, bus contention while sending, or protocol behavior). Neither result alone identifies the exact circuit fault. Restore your original firmware over USB with RJ12 disconnected.
